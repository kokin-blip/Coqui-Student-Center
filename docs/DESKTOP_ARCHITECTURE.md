# Desktop architecture and milestone status

## Runtime boundary

The installed application is authoritative. `apps/desktop-ui/dist` is bundled by Tauri as `frontendDist`; no product page, PWA, service worker, Cloudflare Worker, D1 binding, or browser authentication helper remains. The cloud API is optional and cannot generate the offline plan.

## Local data boundary

The Rust host opens `student-center.db` with SQLCipher and a 256-bit random device master key stored in the operating-system credential service. Imported source files are copied into the app data vault and encrypted with XChaCha20-Poly1305 under unique object keys, which are then wrapped by the device key. Only typed commands are exposed to the React webview.

An optional application PIN adds a second local privacy gate for an already signed-in OS session. A versioned `pin.json` stores Argon2id parameters, a random salt, and an XChaCha20-Poly1305-wrapped copy of the device master key; it contains neither the PIN nor plaintext key. Settings replacement is staged and recoverable, Argon2 work runs off the UI thread, failed unlocks use increasing delays, and a PIN-enabled restart begins locked. Startup returns only security status until unlock succeeds, and every data-bearing Tauri command independently checks the locked state. The database connection and OS-protected key remain resident in the native process, so this gate is intentionally an app privacy control rather than a defense against code executing as the same operating-system user.

The append-only `mutations` table records UUID mutation IDs, logical timestamps, device IDs, operations, and tombstones. It is both the local provenance record and the source for encrypted push. Local-only entity types stay in this log but are filtered out at the sync boundary rather than at write time, so removing a record from replication never silently erases its local history. Normalization produces `import_candidates`; only explicit approval creates or updates canonical records. Field-level `provenance_links` retain the active source evidence for imported critical values.

After optional account sign-in, sync protection is established entirely in Rust. New protection generates a random 256-bit account key and encodes it as a checksummed 24-word English BIP-39 recovery code. The student must confirm three unique randomly selected words before anything persists. Recovery validates all 24 words and the checksum locally. Every setup or recovery also creates a separate random X25519 device private key and UUID; only the public key and non-sensitive status can cross the Tauri IPC boundary. Pending keys use zeroizing native memory, and confirmed account/private device keys are stored as one versioned record in the operating-system credential vault rather than SQLite or browser storage. Device registration, encrypted mutation transport, approval envelopes, and revocation remain separate network steps.

Portable backups use a versioned tar stream inside age passphrase encryption. The payload contains a transactionally consistent SQLCipher snapshot, the prior device key only inside the encrypted envelope, authenticated manifest hashes, and vault objects that are already independently encrypted. Preview consumes and authenticates the whole archive, rejects unknown/duplicate/traversal entries and size abuse, and returns a ciphertext SHA-256 fingerprint. Restore requires that same fingerprint and a second explicit confirmation, validates every document by decrypting it in memory, rewraps each object key, rekeys SQLCipher to the current OS-protected device key, and stages all data before replacing anything. A small restore journal rolls back to the previous database and vault after interruption; successful installation removes the journal before deleting rollback material. Credentials are never exported, and Canvas connections return as `needs_reauthentication`.

- Confirmed 24-word BIP-39 recovery setup and recovery, random per-device X25519 identity generation, zeroizing pending-key memory, OS-credential-vault persistence, locked-state authorization, and a React confirmation/recovery flow that receives no secret private key material.
- Native device registration and encrypted mutation push. The profile binds to one account only after authenticated registration succeeds. Mutation plaintext is encrypted with XChaCha20-Poly1305 under the account key; protocol version, mutation/account/device/entity IDs, logical timestamp, entity type, schema version, and tombstone flag are authenticated as associated data. Each envelope is then signed with the authoring computer's Ed25519 device key over that same metadata plus the nonce and ciphertext — the ciphertext is included because the associated data is authenticated under the *shared* account key, so without it a sibling computer could re-encrypt different plaintext under identical metadata and reuse the original signature. Ciphertext envelopes are written to an encrypted local outbox before upload and reused byte-for-byte until acknowledged, preventing crash retries from reusing a mutation ID with a different nonce/ciphertext.
- Push is gated on device authorization at three independent layers: the API route requires an approved, unrevoked device header and refuses a batch whose mutations claim a different author; an `AuthorizingSyncRepository` decorator wraps every storage adapter so the rule cannot depend on which one is injected; and the row-level insert policy requires a matching approved, unrevoked device row. The service also verifies each envelope's signature against the pushing device's registered signing key before storing it.
- Cursor-based encrypted pull, signature verification, and deterministic local merge. A downloaded envelope must verify against the sender's signing key — held in a local `sync_devices` table that pins each peer's key on first use, so a hostile service cannot substitute its own — before the AEAD runs. Duplicate mutation IDs must retain byte-identical envelopes. Merge is last-writer-wins on `(logical timestamp, device id)` with an observed-remove set for task dependencies; critical academic dates are never silently overwritten but recorded as `sync_critical_date` conflicts for review. An envelope whose entity type this build does not map is stored with `outcome='deferred_unknown_type'` and left out of the version register, then replayed in logical order on the next pull after an upgrade. Inbound classification is deliberately two-valued — mapped or deferred — and never consults the local-only list, because a build that predates a type becoming replicated would otherwise discard a peer's real records instead of holding them.
- One predicate governs replication. `canonical_table` is the sole mapping, `is_replicated_entity_type` is derived from it, and it is applied at the outbox, the pending count, the local version-register write, and the apply path. Plans, plan blocks, documents, reminders, notification preferences, and integration connections are declared local-only and filtered out in SQL before the outbox page limit, so high-churn local records cannot starve real uploads.

- Encrypted portable export, authenticated preview, explicit restore confirmation, cross-device database/object-key rekeying, and interruption rollback.

The HTTPS release endpoint and Tauri public verification key are compile-time trust anchors; normal development/CI builds have no update channel, expose no updater permissions to the webview, and cannot install an update. Release-only updater artifacts are enabled by the separate `tauri.release.conf.json` overlay and require signing secrets outside the repository.

The Windows release executable and NSIS artifact now bundle and pass the real PDFium-to-PNG-to-Tesseract smoke path. Supply-chain selection is complete: immutable hashed PDFium archives replace Poppler, Tesseract 5.5.2 is built statically from a pinned vcpkg baseline, signed official English trained data is pinned, transitive notices are collected, and each desktop CI lane enforces a source-bound runtime lock before packaging.
- Account-key rotation on device revocation (see Known limitations below), and richer mergeable payloads for the entity types that are currently local-only.
- Accessibility and installed-app end-to-end coverage on both target platforms. There is currently no automated accessibility testing, no keyboard handling outside native controls, and the one modal declares `aria-modal` without a focus trap or Escape handling.
- Deployment validation of the SQL and private-bucket migrations against a real Supabase project.

The production cloud API now requires Supabase configuration and uses PostgREST with the verified user's access token, so RLS remains an active defense. A shared conformance suite (`services/cloud-api/test/repository-conformance.test.ts`) runs every case against both the in-memory and PostgREST-backed adapters, driven by a small PostgREST double. This exists because the unauthorized-push defect survived review precisely by living in only one adapter: the rule was enforced in the in-memory test double while production had no gate at all. The suite proves HTTP shaping and shared-invariant participation; it deliberately cannot prove row-level security, database constraints, or triggers, which remain asserted as migration text in `security.test.ts` and still require deployment validation against a real Supabase project before synchronization is released.

## Known limitations

Revocation is enforced by the service and the database, not cryptographically. A revoked computer keeps the account key and the data it already downloaded; what it loses is the ability to read or write anything new. Rotating the account key would require a `keyEpoch` bound into the associated data and the signed message, re-wrapped approval envelopes delivered to every remaining authorized computer, an epoch barrier on pull so a computer cannot silently fail to decrypt post-rotation mutations, a re-encrypt-or-dual-decrypt strategy for the existing mutation log and every encrypted object manifest, and an interface for "every other computer must come online before rotation completes." That is larger than the current sync surface combined, and it protects only future mutations — it cannot un-disclose the past — so it is deferred rather than bundled with the gating work that makes revocation meaningful today.

Any authorized computer can read all of the account's synchronized data; the account key is shared by design, and signatures establish authorship rather than read access.
