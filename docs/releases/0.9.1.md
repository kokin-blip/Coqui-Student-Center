# Coqui Student Center 0.9.1

Repairs the macOS build. 0.9.0 was the first release published as a download,
and its DMG could not be opened on any Mac: macOS reported "the application is
damaged and cannot be opened" and offered no way past it. This release contains
no product changes. It exists because the artifact was unusable.

## What was actually wrong

The 0.9.0 diagnosis in that release's notes — "macOS is Gatekeeper-blocked and
needs right-click → Open on first launch" — was wrong on both counts.

`bundle.macOS` in `tauri.conf.json` carried a `minimumSystemVersion` and nothing
else. With no `signingIdentity` set and no `APPLE_SIGNING_IDENTITY` in the
release workflow, the Tauri bundler never ran `codesign` over the assembled
`.app`. What shipped was not an unsigned app; it was an inconsistently signed
one. The Rust linker ad-hoc-signs Mach-O output automatically, so all three
binaries inside the bundle — `Contents/MacOS/student-center`, and the bundled
`tesseract` and `libpdfium.dylib` under `Contents/Resources/ocr` — carried valid
`linker-signed` signatures, while the bundle around them had no
`Contents/_CodeSignature` directory at all:

```
$ codesign --verify --deep --strict "Coqui Student Center.app"
Coqui Student Center.app: code has no resources but signature indicates they must be present

$ codesign -dvvv "Coqui Student Center.app"
CodeDirectory ... flags=0x20002(adhoc,linker-signed)
Sealed Resources=none
Info.plist=not bound
```

Gatekeeper reads a signature that claims sealed resources over a bundle that has
none as evidence of tampering, and "damaged" is the verdict it reports for
tampering. That is a different failure from the ordinary unsigned-app prompt,
and it matters because the escape hatches are different: an unsigned app can be
admitted from System Settings, while a bundle judged damaged is simply refused.

The second error was in the workaround. Control-clicking an app and choosing
Open has not bypassed Gatekeeper since macOS 15; the admission control moved to
System Settings. The advice in the 0.9.0 notes would not have worked even
against the failure it described.

## The fix, and the gate that matters more

`bundle.macOS.signingIdentity` is now `-`, Apple's ad-hoc pseudo-identity. The
bundler signs the `.app` after resources are copied and before the DMG is built,
which produces the `_CodeSignature/CodeResources` seal whose absence caused the
failure. It is a one-line change.

The one-line change is not the interesting part. 0.9.0 shipped broken because
nothing in the pipeline could tell a sealed bundle from an unsealed one — the
release workflow built it, checksummed it, and published it, and every step
reported success. `npm run macos:verify-signature` closes that gap. It asserts
that `Contents/_CodeSignature/CodeResources` exists, that `codesign --verify
--strict` passes, that the code directory reports sealed resources and is not
merely `linker-signed`, and that every Mach-O file found anywhere under
`Contents/` verifies on its own. It runs on the macOS leg of both `Desktop CI`
and `Release`, between packaging and checksums, and fails the job rather than
publishing.

It is deliberately modelled on `ocr:verify --require-ready`, which has guarded
the OCR runtime the same way since 0.7.0. The lesson 0.9.0 taught is that a
build step that cannot fail is not a check.

The gate reads the `.app` back out of the finished disk image rather than
inspecting the staged copy, because the bundler deletes that copy as soon as the
DMG exists — it logs `Cleaning .../bundle/macos/Coqui Student Center.app` and
removes it. Mounting the DMG is the stronger check regardless: the disk image is
what a student downloads, and nothing else in the pipeline looks inside it.

The bundled OCR binaries are covered too. They live under `Contents/Resources`
rather than `Frameworks`, so the bundler treats them as data and the bundle seal
only hashes them; `tesseract` is spawned as its own process and needs a
signature Gatekeeper accepts independently. The gate verifies each one directly
instead of trusting the bundle's seal to speak for them.

## What a Mac user still sees

Ad-hoc signing proves the bundle has not been altered since it was built. It
proves nothing about who built it, because there is no Apple-issued identity
behind it. So the first launch of a downloaded build is still refused, now with
the honest message rather than the misleading one:

> "Coqui Student Center" can't be opened because Apple cannot check it for
> malicious software.

Admitting it once, per machine: **System Settings → Privacy & Security**, scroll
to the notice naming the app, **Open Anyway**, then **Open** in the confirmation
dialog. Every later launch is silent. Control-click → Open does not work; use
System Settings.

Removing that step requires an Apple Developer Program membership, a Developer ID
certificate, and notarization. There is no free path to a warning-free download,
and this release does not pretend otherwise. When the membership exists, the only
change is replacing `-` with the real identity and adding the certificate and
Apple ID secrets to the release workflow; the gate keeps working unchanged.

## Verification

- The gate was proven against the published artifact, not a synthetic one: run
  against `Coqui.Student.Center_0.9.0_aarch64.dmg` as downloaded from the 0.9.0
  release page, it exits 1 and reports the missing seal, the failed
  `codesign --verify`, `Sealed Resources=none`, and the `linker-signed` flag. It
  exits 0 on the same bundle after an ad-hoc re-sign.
- Seven tests in `scripts/test/macos-signature.test.mjs` cover an unsealed bundle
  reproducing the 0.9.0 shape, a missing bundle, an ad-hoc signed bundle, the
  target-to-path mapping, and real DMG round-trips in both the passing and
  failing direction. The whole `scripts` suite passes.
- The first version of this gate was itself caught by CI: it looked for the
  staged `.app` that the bundler had already deleted, and failed the macOS leg
  rather than passing silently on an artifact it never opened.
- **The macOS build is verified by hand this time.** 0.9.0 was packaged and
  tested on a runner but never installed on a real Mac, which is precisely how an
  unopenable DMG reached a release page. The 0.9.1 DMG was downloaded through a
  browser so it carried a genuine `com.apple.quarantine`, installed to
  `/Applications`, and launched on Apple Silicon macOS 26.6.1 with no repair
  commands run.

## Known limitations

- **The Windows build is still unsigned** and shows the SmartScreen warning. Same
  root cause, different fix, not addressed here.
- **macOS still needs one Open Anyway per machine.** Ad-hoc signing removes the
  damaged verdict; only notarization removes the prompt.
- The updater remains inert: the endpoint is unset, no updater artifacts are
  produced, and the release check returns "not available". Updating means
  downloading the next build by hand.
- Soft revocation is a known limitation, not a half-implemented feature: key
  rotation cannot un-disclose what a revoked computer already downloaded.

## Artifacts

Built and published by the `Release` workflow from tag `v0.9.1`. Sizes and
digests are recorded in a follow-up commit once the workflow publishes, matching
how 0.9.0's artifacts were recorded.

Each ships a `.sha256` sidecar. Note that GitHub substitutes dots for the spaces
in the asset names on the release page, so a downloaded file is named
`Coqui.Student.Center_0.9.1_...`; the sidecar records the original name, which
matters if you verify with `sha256sum -c` rather than comparing the digest.

Schema stays at version 11; no migration is required.
