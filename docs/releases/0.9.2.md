# Coqui Student Center 0.9.2

Setup stopped hiding the school a student actually attends, course fields
learned what a real course is, and an imported class schedule became a
schedule rather than a pile of dates.

## The school search could not find the school

Searching "Arizona State" returned twelve satellite locations — Cochise, Pima,
Yuma, Tucson, Washington D.C. — and none of the three campuses anyone attends.

The data was never missing. `search_institutions_in` filtered the directory in
raw file order and cut at twelve. ASU has seventeen entries, and the ones a
student wants sit at positions thirteen through seventeen. Entry `104151` — the
only one carrying the campus picker and registrar term dates — was unreachable
by any query at all.

- Results are **scored** now instead of taken in file order, and an entry with
  campus and term presets outranks a branch location that carries only a name.
- **Campus names are searchable.** "Tempe" appears nowhere in ASU's name, which
  is why that search returned nothing; it now reaches Arizona State and
  pre-selects the campus that matched.
- **Acronyms resolve**, so "asu" works. Both are anchored to word boundaries,
  because a plain substring search for "asu" returned "Beyond Measure Barbering
  Institute" and "Treasure Coast Technical College" while hiding every Arizona
  State campus.

## A student can attend more than one campus

Tempe, West Valley and Downtown Phoenix at once is ordinary. The campus step is
a set now. The first pick stays primary and keeps filling the location on new
class meetings, and "Online or multiple campuses" replaces the set rather than
joining it, because it is a statement that no single campus applies.

Profiles saved before this keep their campus: the new list defaults empty and
the original field is still read.

## Course fields knew eleven courses

Course autocomplete offered a hardcoded list — `MAT 142`, `ENG 101`, `PSY 101`
— and `search_course_suggestions` ignored the school entirely. Its institution
parameter was bound to `_institution_id` and never read, so every school in the
country got byte-identical suggestions. An ASU student typing `CSE 240` matched
nothing.

The school is read now, against a per-institution catalog: 133 ASU courses and
381 sections across all four campuses. Picking a section fills the weekdays,
start, end, location and instructor rather than leaving a schedule to be
retyped, and the picker states which term the sections describe.

Autocomplete also reached the two places it was missing. The Courses tab had
none at all — two plain text boxes — and quick capture could not name a course,
because `add_task` never accepted one even though `tasks.course_id` has existed
all along.

### Where the course data comes from, and what that costs

ASU publishes no usable course API. The class search behind
`catalog.apps.asu.edu` answers 401 to anyone anonymous and authenticates through
`weblogin.asu.edu` with an OAuth2 code grant; the legacy public search redirects
into it; and `catalog.asu.edu` carries policy pages, not courses. Reading it
programmatically would mean defeating an access control, so nothing in this app
does.

The catalog is built offline from Class Search pages a student exported
themselves, by `catalog:prepare`. That has consequences worth stating plainly:

- **Coverage is only what was exported.** Four General Studies categories plus
  CSE 240. It is not the ASU catalog.
- **Sections are Fall 2026.** They go stale when the term turns over, which is
  why the picker says which term it is showing.
- **Open seats are deliberately absent.** They are wrong within hours, and a
  stale seat count in a bundled file is worse than no number.

`catalog:verify` gates it in CI and in the release lane. It found three real
defects on its first run, in data already committed: a page break splices the
running header into a row, merging it with the start time, and those sections
were being written with weekdays and no clock.

## An imported class schedule was forty-five separate things

ICS import parsed recurrence and then expanded it, writing one commitment per
occurrence over a 180-day horizon. A class meeting three times a week became
about forty-five disconnected rows. Moving the class meant editing every one,
the timetable showed a wall of one-off entries instead of a weekly pattern, and
the class simply stopped at the horizon.

A plain `FREQ=WEEKLY` rule now becomes one class meeting series — the same
record onboarding creates, already replicated between a student's computers.
Approving it matches the course on title or code before creating one, so
importing twice does not leave two of every class, and files it under the term
that actually contains the first meeting.

The collapse is deliberately narrow. An interval, a positional selector like
`BYDAY=2MO`, or any non-weekly frequency keeps the old expansion. A rule that
cannot honestly be stated as "every week on these days" must not be flattened
into a schedule that was never in the file.

**Canvas still produces commitments.** It expands recurrences server-side, so
there is no rule to read, and collapsing would mean inferring a pattern from
repeated titles and times. That guess is not shipped.

## Verification

- 104 native Rust tests, 22 UI tests, 28 script tests and 44 cloud-service tests
  pass; every workspace typechecks.
- The school search, campus multi-select, section picker, both autocomplete
  surfaces and the review screen were each driven in the running application,
  not only asserted in tests. That is what caught the campus primary failing to
  reassign on deselection.
- Two parser bugs were found by checking output against the source rather than
  trusting a clean run: indented rows made leading whitespace a column
  delimiter, and closing a title at the instructor name aborted the scan for the
  course code, silently reducing a hundred-class file to one record.
- The predicted approval bug happened. Candidate kind is switched on in several
  places and one was missed, so approving an imported class failed on an entity
  type it had never been taught.

## Known limitations

- **Neither build is signed by a real identity.** macOS is ad-hoc signed and
  needs one **System Settings → Privacy & Security → Open Anyway** per machine;
  Windows shows SmartScreen. Notarization needs an Apple Developer membership.
- The updater remains inert. Updating means downloading the next build by hand.
- Imported class meetings default to a `lecture` component with no location; the
  calendar `LOCATION` field is not read yet.
- Commitments already imported from a recurring event are left alone. Nothing
  collapses them retroactively.
