# Coqui Student Center 0.9.0

Rebuilds the interface on a semantic token system with five themes, makes a
year's worth of orphaned commands reachable, and closes a sync hole that let an
unauthorized computer write to the encrypted mutation log.

This is the first release published as a downloadable build for both Windows and
Apple Silicon. Everything through 0.8.0 was built locally and never distributed.

## Appearance is a real system now

- Colour lived in two competing places: a 2,779-line stylesheet holding 281
  hardcoded hex values, and `experience-overrides.css`, a half-finished token
  migration layered on top. The dark theme was written out twice, once for
  `[data-theme="dark"]` and again inside a `prefers-color-scheme` block.
- `tokens.css` now owns appearance — semantic colour tokens plus spacing, radius,
  typography and motion scales, five themes (Coqui Dark, Midnight, Graphite,
  Forest, Light) and six accents. Themes and accents are independent; accent
  variants are derived with `color-mix`, so one accent definition reads correctly
  on every theme.
- "System" resolves to a concrete theme in JS rather than duplicating a media
  query per theme.
- Legacy variable names are aliased onto the new tokens rather than rewritten, so
  the whole stylesheet themes correctly without 2,779 lines changing first.
- **Settings is its own destination.** The theme and accent persistence shipped
  first, but the only control was a three-way topbar toggle — Midnight, Graphite,
  Forest and every accent were built, stored, tested, and impossible to select.
  The previews render the real palettes by carrying `data-theme` and
  `data-accent` themselves, so no palette value is duplicated into JS.
- Settings had also been sitting under a label and icon that opened the lock
  screen. App lock is now separate from Settings.
- Existing profiles keep their theme: the pre-0.9 `dark` maps onto Coqui Dark.

## The shell and the reading order

- The next-action card was a saturated teal gradient with white text, which made
  the most-read element on the screen also the loudest. It is a normal raised
  surface now, with the accent confined to the eyebrow icon, a 3px left
  indicator, and the primary button.
- That exposed the button system: `.primary` was a white button and `.ghost` a
  white-outlined one, both designed to sit on teal and both effectively invisible
  anywhere else. Primary, secondary, ghost and danger are now defined against
  tokens, each with a focus ring visible on every surface.
- Capacity used to render "0h 0m remaining / 0 completed / 0 conflicts" against
  an empty plan, which tells a new student nothing. With no blocks it explains
  what would make the number meaningful; with blocks it reports what actually
  fills the day. Conflict state is an icon plus words, not colour alone.
- Assignments and Courses emitted identical markup and were told apart only by
  positional CSS (`:first-child` / `:nth-child(2)`). Reordering a panel silently
  merged the two screens. The view now decides which panels belong to which tab.

## Records that could be created but never changed

Nine commands had a Rust implementation and a `native.ts` wrapper but no caller
anywhere in the interface.

- **Academic terms** had no post-setup UI at all — a term could only ever be set
  during onboarding. They now have a panel with create, edit, delete, and a
  current-term toggle.
- **Instructors and class times** were add-only. Each row now carries Edit and
  Remove.
- **Academic events** were listed and added, but never edited or removed.
- **Quick Add** collected a title and an estimate and called `addTask` without
  the `dueAt` argument it accepts, so everything captured there reached the
  planner with no deadline to schedule against. It now has an optional due field.
- The topbar **Search** button had no `onClick` and no command behind it. It now
  searches courses, assignments and commitments, each result linking to the tab
  that owns it. No new native command was needed — the data was already there.

## Sync correctness

- **Push was not gated on device authorization.** The route checked the access
  token but not the device, the Supabase adapter had no check at all, and the RLS
  insert policy verified only the account — so a pending or revoked computer
  could append to the immutable mutation log. The contract test that should have
  caught this passed because it exercised the in-memory adapter alone. Push is
  now gated at the route, in a decorator wrapping every adapter, and in an RLS
  policy requiring an approved, unrevoked device, with a conformance suite
  running every shared invariant against both adapters.
- **Mutation envelopes are signed** with each computer's Ed25519 device key
  (envelope v3). The signature covers metadata, nonce and ciphertext — omitting
  the ciphertext would let a sibling device re-encrypt different plaintext under
  identical metadata and reuse the original signature. Peer keys are pinned on
  first use. A golden vector pins the signing bytes on both sides of the
  Rust/TypeScript boundary.
- Instructors, class times and academic events were **unsyncable and reported
  failure after saving**: `canonical_entity_snapshot` had no arm for the three
  types added in 0.7.0 and its fallthrough is a hard error, so the row was
  written and the command still returned "Unsupported canonical mutation entity
  type". `canonical_table` omitted them too, so a second device would have
  discarded them silently.
- The six local-only entity types are no longer replicated. They were encrypted,
  uploaded, downloaded and discarded, and they advanced the version register on
  both paths — a high-water mark that would have swallowed the first real
  mutation if such a type ever became replicated.
- Staging is real. `applied=0` was unreachable because pull applied inside the
  same transaction, so the "safely staged" banner was dead code. Mutations whose
  entity type this build does not recognise are now held and drained after an
  upgrade.

## Verification

- 94 native Rust tests, 22 UI render tests across 6 files, 5 shared-contract
  tests and 44 cloud-service tests pass.
- `apps/desktop-ui` had no test runner before this cycle; it now runs vitest with
  jsdom and Testing Library against the real interface.
- Several tests were verified by mutation rather than assumed: renaming a call
  site fails the wrapper-coverage test, and leaking the task editor into Courses
  fails the tab suite.
- Both installers were built and published by the `Release` workflow, which
  enforces the OCR readiness gate (`ocr:verify --require-ready`) before packaging
  and runs the native test suite on each shipping target.

## Known limitations

- **Neither build is signed.** Windows shows the SmartScreen warning. macOS is
  Gatekeeper-blocked and needs right-click → Open on first launch. Signing and
  notarization credentials are still outstanding.
- The updater remains inert: the endpoint is unset, no updater artifacts are
  produced, and the release check returns "not available". Updating means
  downloading the next build by hand.
- **The macOS build is unverified by hand.** It compiles, packages, and passes
  the native test suite on an Apple Silicon runner, but no one has installed and
  run it on a real Mac. Treat it as an early private beta.
- Soft revocation is a known limitation, not a half-implemented feature: key
  rotation cannot un-disclose what a revoked computer already downloaded.

in the asset names on the release page, so a downloaded file is named
`Coqui.Student.Center_0.9.0_...`; the sidecar records the original name, which
matters if you verify with `sha256sum -c` rather than comparing the digest.
